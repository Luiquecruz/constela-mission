# Caching Strategies in CI/CD

Caching is a fundamental optimization mechanism in CI/CD pipelines. By storing and reusing intermediate build outputs, downloaded library packages, and container compilation layers across pipeline runs, caching dramatically reduces pipeline execution time and network bandwidth. However, improperly configured cache systems introduce non-determinism, build corruption, and supply chain security vulnerabilities.

## Case study

In the analysis of the attack on a popular Python package, the registry operator reports that the attack targeted the GitHub Actions cache used during the build, so that releases carried code the project had not written. Nothing was exploited through a bug in the cache itself: what a low-trust run could write, a later build restored and trusted. A cache key must come from the content that matters, and what a low-trust job writes must not feed a high-trust job.

## Dependency and Build Layer Caching

CI/CD runners operate in clean, ephemeral environments that start with zero local state. Downloading third-party library dependencies (such as `node_modules` or `go/pkg/mod`) on every single pipeline run consumes significant network bandwidth and inflates execution time.

Pipeline caching restores speed through two main mechanisms:

- **Dependency Caching**: Storing downloaded external library packages in a central object cache and restoring them to the runner workspace before the build step begins.
- **Build Layer Caching**: Reusing pre-compiled binary compilation layers (such as Docker BuildKit layers) when underlying source files have not changed.

Layer caching works only if the Dockerfile orders its instructions from the least to the most changing, so that editing source code does not invalidate the dependency layer:

```dockerfile
FROM node:lts-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build
```

::: github
Layer caching reuses the unchanged layers of the image. In GitHub Actions, Buildx stores them in the cache service:

```yaml
- uses: docker/build-push-action@v6
  with:
    push: true
    tags: ghcr.io/org/api-service:1.0.0
    cache-from: type=gha
    cache-to: type=gha,mode=max
```
:::

::: azure
In Azure Pipelines, pull the previous image and let Docker reuse its layers:

```yaml
- script: |
    docker pull myregistry.azurecr.io/api-service:latest || true
    docker build --cache-from myregistry.azurecr.io/api-service:latest -t myregistry.azurecr.io/api-service:$(Build.BuildId) .
  displayName: Build with layer cache
```
:::

::: aws
In AWS CodeBuild, the project can keep the layers on the build host:

```bash
aws codebuild update-project --name api-service --cache type=LOCAL,modes=LOCAL_DOCKER_LAYER_CACHE
```
:::

::: gcp
In Google Cloud Build, tell Docker which image to take layers from:

```yaml
steps:
  - name: gcr.io/cloud-builders/docker
    args: [build, --cache-from, REGION-docker.pkg.dev/PROJECT_ID/apps/api-service:latest, -t, REGION-docker.pkg.dev/PROJECT_ID/apps/api-service:$SHORT_SHA, .]
```
:::

## Deterministic Cache Keys and Fallback Resolution

To ensure cache safety, cache storage and retrieval must be governed by deterministic cache keys generated from cryptographic hashes of project manifests.

A robust cache key strategy follows a structured pattern:

1. **Primary Cache Key**: Generated by hashing dependency lockfiles (e.g., `cache-${runner.os}-${hashFiles('package-lock.json')}`). If `package-lock.json` has not changed, the pipeline achieves a 100% cache hit.
2. **Fallback Restore Keys**: If an exact lockfile match is not found (e.g., when a dependency was updated in a PR branch), the pipeline falls back to prefix matching (e.g., `cache-${runner.os}-main-`) to restore partial dependencies rather than starting from scratch.

A key derived from the lockfile changes whenever the dependencies change, so the build looks for a new cache entry instead of reusing a stale one. The old entry is not deleted, and a restore key can still select it, which is why fallback keys restore only partial matches.

::: github
All four providers cache with the same three ideas: a key derived from the lockfile, optional fallback keys, and a path to save. GitHub Actions looks in the cache of the current branch first, the exact key, then a prefix match on the primary key, then each restore key in order, and only then in the cache of the base branch and of the default branch; a run never restores caches written by sibling branches. The challenge models a simplified version of that search:

```yaml
- uses: actions/cache@v6
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-npm-
```
:::

::: azure
Azure Pipelines uses the `Cache@2` task with the same fields:

```yaml
- task: Cache@2
  inputs:
    key: 'npm | "$(Agent.OS)" | package-lock.json'
    restoreKeys: |
      npm | "$(Agent.OS)"
    path: $(Pipeline.Workspace)/.npm
```

Azure Pipelines restores and saves a cache with the `Cache@2` task, keyed by the lockfile:

```yaml
- task: Cache@2
  inputs:
    key: 'npm | "$(Agent.OS)" | package-lock.json'
    path: $(Pipeline.Workspace)/.npm
- script: npm ci --cache $(Pipeline.Workspace)/.npm
```
:::

::: aws
AWS CodeBuild declares the cache in the buildspec and stores it in the project's cache bucket:

```yaml
cache:
  key: npm-$(codebuild-hash-files package-lock.json)
  fallback-keys:
    - npm-
  paths:
    - /root/.npm/**/*
```

AWS CodeBuild lists the paths to keep between builds in the buildspec, and the project must have a cache type enabled:

```yaml
cache:
  paths:
    - node_modules/**/*
```
:::

::: gcp
Google Cloud Build has no key-based dependency cache of its own. Teams cache container layers with Kaniko, which pushes layers to a registry and reuses them on the next build:

```yaml
steps:
  - name: gcr.io/kaniko-project/executor:latest
    args:
      - --destination=REGION-docker.pkg.dev/PROJECT_ID/apps/api-service:$SHORT_SHA
      - --cache=true
```

Google Cloud Build can reuse the layers of an image when it builds with Kaniko and the cache turned on:

```yaml
steps:
  - name: gcr.io/kaniko-project/executor:latest
    args:
      - --destination=REGION-docker.pkg.dev/PROJECT_ID/apps/api-service:$SHORT_SHA
      - --cache=true
```
:::

## Cache Poisoning and Security Risks

Cache systems introduce unique supply chain security risks if access controls and isolation rules are omitted.

Key security threats include:

- **Cache Poisoning via Unreviewed Pull Requests**: An attacker submits a malicious PR that modifies build scripts to inject malware into shared cache archives. If subsequent builds on `main` restore this poisoned cache, the malware executes inside production build runs.
- **Cross-Branch Cache Pollution**: Allowing feature branches to overwrite the primary cache key of the `main` branch causes instability across the engineering team.
- **Caching Sensitive Data**: Accidental inclusion of API keys, SSH keys, or environment tokens inside cached directories exposes secrets to unauthorized branches.

To mitigate these risks, pipeline platforms enforce cache isolation rules: pull request builds may read caches from `main`, but only jobs executing on the protected `main` branch are authorized to write or update primary cache entries.

::: github
Let pull requests read the cache but only the trunk write it. In GitHub Actions, split restore and save:

```yaml
- uses: actions/cache/restore@v5
  with:
    path: ~/.npm
    key: npm-${{ hashFiles('package-lock.json') }}
- run: npm ci
- uses: actions/cache/save@v5
  if: github.ref == 'refs/heads/main'
  with:
    path: ~/.npm
    key: npm-${{ hashFiles('package-lock.json') }}
```
:::

::: azure
In Azure Pipelines, run the task that saves the cache only for the trunk:

```yaml
- task: Cache@2
  condition: eq(variables['Build.SourceBranch'], 'refs/heads/main')
  inputs:
    key: 'npm | "$(Agent.OS)" | package-lock.json'
    path: $(Pipeline.Workspace)/.npm
```
:::

::: aws
In AWS CodeBuild, give the project of pull requests its own cache location, apart from the one of the trunk:

```bash
aws codebuild update-project --name api-service-pr --cache type=S3,location=BUCKET/pr
```
:::

::: gcp
In Google Cloud Build, point the layer cache of pull requests at a repository that releases never read:

```yaml
steps:
  - name: gcr.io/kaniko-project/executor:latest
    args:
      - --destination=REGION-docker.pkg.dev/PROJECT_ID/apps/api-service:$SHORT_SHA
      - --cache=true
      - --cache-repo=REGION-docker.pkg.dev/PROJECT_ID/cache-pr/api-service
```
:::

## Across the platforms

The branch rule is a security rule. If a pull request from a fork could write a cache that the default branch later restores, the pull request would run code in the production build; that is what cache poisoning means.

## Common mistakes

- **Caching without lockfile hashing**: Using static or non-deterministic cache keys (such as `cache-v1`) results in stale dependency pollution and non-reproducible builds.
- **Allowing feature branches to overwrite main branch cache**: Failing to isolate cache write permissions allows unreviewed PR branches to poison shared build caches.
- **Caching compiled application artifacts instead of dependencies**: Caching application build outputs across commits risks bundling outdated code into new releases.

## In practice

Try it in a repository of your own.

1. Cache the dependencies with a key built from the lockfile.
2. Run the pipeline twice and compare the times. Change one dependency and confirm that the key changes and the cache is rebuilt.
3. Check which workflows are allowed to write to the cache and restrict writing to the trusted ones.

The challenge generates the cache key and resolves a restore with fallback keys.
