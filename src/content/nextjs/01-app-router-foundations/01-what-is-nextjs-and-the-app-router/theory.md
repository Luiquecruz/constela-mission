# What Is Next.js and the App Router?

React itself is a **UI library**: it renders components and reconciles updates in the DOM, but it intentionally leaves routing, code splitting, server rendering, bundling, and data caching up to you. If you start with a client-only Single-Page Application (SPA) built with Vite, the browser receives a near-empty HTML shell and a JavaScript bundle, parses that JavaScript, and only then begins fetching data and painting content. For production web applications that need fast initial loads, strong SEO, backend endpoints, and fine-grained caching, teams need a full-stack React framework.

**Next.js** is that framework. It pairs React with a file-system router, a multi-environment bundler, server-side rendering and streaming, static optimization, image/font optimization, and built-in caching primitives.

## App Router vs. Legacy Pages Router

Next.js supports two routing architectures: the legacy **Pages Router** (`pages/`) and the modern **App Router** (`app/`).

| Dimension | Legacy Pages Router (`pages/`) | Modern App Router (`app/`) |
| --- | --- | --- |
| Component model | Client-hydrated React by default | **React Server Components** by default; opt into `'use client'` |
| Data fetching | Page-level `getServerSideProps` / `getStaticProps` | Async Server Components fetching directly where data is used |
| Shared layouts | Manual wrapper patterns inside `_app.tsx` | Native nested `layout.tsx` files per route segment |
| Loading & errors | Custom state flags or global `_error.tsx` | Built-in `loading.tsx`, `error.tsx`, and `not-found.tsx` conventions |
| Streaming | Whole-page HTML response | Granular streaming via `<Suspense>` and `loading.tsx` |

In the App Router, only routes with a `page.tsx` file become publicly reachable URLs, which lets you colocate helper utilities, tests, and components right inside route folders.

## Project Anatomy

A typical Next.js App Router project starts with a clean, predictable directory layout:

```text
my-next-app/
├── app/
│   ├── layout.tsx      # Root layout: defines mandatory <html> and <body> tags
│   ├── page.tsx        # Home route rendered at "/"
│   └── globals.css     # Global styles imported by the root layout
├── public/
│   └── logo.svg        # Static assets served directly from "/" (e.g. "/logo.svg")
├── next.config.ts      # TypeScript config for images, redirects, headers, compiler options
└── package.json        # Scripts: dev, build, start
```

- **`app/layout.tsx`**: The root layout wraps every page in your application. It is the only required layout and must render the `<html>` and `<body>` elements.
- **`app/page.tsx`**: The entry UI for `/`. Export a React component as `default` and Next.js automatically turns it into a server-rendered route.
- **`public/`**: Files placed here are served as static assets from the root URL path without passing through the bundler.
- **`next.config.ts`**: Central configuration for domain image allowlists, HTTP headers, URL redirects, and framework options.

## Development, Build, and Runtime Commands

Next.js organizes the application lifecycle around three core CLI commands defined in `package.json`:

1. **`next dev`**: Starts the local development server with **Turbopack**, providing rapid incremental compilation and React Fast Refresh as you edit files.
2. **`next build`**: Compiles the production application, splits server and client bundles per route, prerenders static routes, and prepares optimized output.
3. **`next start`**: Boots the Node.js production server using the artifacts generated by `next build`.

## Server Components by Default vs. `'use client'`

A defining mental model of the App Router is **server-first rendering**. Every file inside `app/` is a **React Server Component (RSC)** by default:

```tsx
// app/page.tsx — runs only on the server
import { getFeaturedCourses } from '@/lib/courses';
import { EnrollButton } from './EnrollButton';

export default async function HomePage() {
  const courses = await getFeaturedCourses();

  return (
    <main>
      <h1>Course Catalog</h1>
      <ul>
        {courses.map((course) => (
          <li key={course.id}>
            <span>{course.title}</span>
            <EnrollButton courseId={course.id} />
          </li>
        ))}
      </ul>
    </main>
  );
}
```

Because `HomePage` executes solely on the server, it can be `async`, read databases or environment secrets safely, and ship zero component JavaScript to the browser. When a leaf element needs browser interactivity—such as `useState`, `useEffect`, or click handlers—you place `'use client'` at the top of that specific file (`EnrollButton.tsx`). Later modules explore how Next.js serializes props across this boundary with React Flight.

## Common Pitfalls

- **Treating `app/` like a client-only SPA**: Adding `'use client'` to `app/layout.tsx` or `app/page.tsx` forces the entire subtree into the client bundle and blocks `async` Server Component data fetching. Keep `'use client'` pushed down to small interactive leaves.
- **Mixing `pages/` and `app/` conventions**: Hooks like `useRouter` from `next/router` belong to the legacy Pages Router and fail in the App Router, which uses `next/navigation` instead.
- **Placing secrets inside `public/` or `'use client'` files**: Everything in `public/` is publicly downloadable, and everything imported into a `'use client'` file ships to the user's browser.

## When to choose it

- **Choose Next.js App Router** when building production web applications that benefit from server-side rendering, SEO metadata, fast first-paint HTML, nested layouts, co-located backend endpoints, and automatic server/client bundle splitting.
- **Choose a client-only React SPA (such as Vite)** when building an embeddable widget, an offline-first desktop wrapper (Electron/Tauri), or a purely client-side tool deployed to static object storage with no need for server rendering or per-route HTML optimization.
